# Blameless review: five client-discovered outages, Oct 16–21 2026

**Evidence basis.** This review is built from what was measured in earlier sessions (prod curls, pm2/nginx/Icecast/LiveKit log excerpts read on the boxes, code in the three repos, the Sep 30 backend snapshot) and from the code as it is today. The full raw-log collection requested for this review has not happened yet: `Desktop/evidence2026-10-22C02/` is empty and this session could not SSH to the boxes. Every claim below is tagged **PROVEN** (a measurement or a log line exists), **PROVEN IN CODE** (the behaviour is unambiguous from the source) or **INFERRED** (consistent with the evidence, not demonstrated). `../evidence/README.md` lists what will settle each INFERRED item.

No names, no blame: every failure here was built into the system by reasonable decisions made under time pressure, and most of them were invisible because nothing was watching.

## Systemic causes

Each incident is a different proximate cause. Five different causes in seven days is itself the finding: the platform has no margin, so whichever weak point the day's circumstances touch becomes the outage. The weak points:

**A. One shared publisher identity (`admin`) for every DJ, every tab, every device.** LiveKit allows one connection per identity per room, so a second Go Live page is not "a second DJ", it is a kick of the first. Nothing in the UI says so. The panel maps every DJ to the station owner's id (`middleswares/auth.js`), which is also why one room serves all DJs. → #5 directly; the most plausible explanation of #2. **PROVEN** mechanism.

**B. Live state lives only in the memory of a single, crash-prone process.** `roomsowners`, `listeners`, `roomCurrentSongPlay`, `welcomeTonesPlayed` are plain objects in `server.js`. The process has died at show start at least six times since July (#1); each restart forgets who is live and which tones played, and the listeners are never told. → #1, and the amplifier for every other failure. **PROVEN**.

**C. Two independent truths with no reconciliation.** "Live" exists twice: the socket backend's opinion (`owner-join` was received) and LiveKit's fact (an `admin` participant is publishing a mic). The website trusts the socket to **mute Auto DJ** and LiveKit to **show the badge**; when they disagree you get either dead air (#5: socket live, LiveKit empty) or Auto DJ over the DJ (#4: LiveKit live, listeners in the wrong room). Nothing compared them, so both failure modes were discovered by listeners. **PROVEN IN CODE**.

**D. No reconnection or resync paths.** Panel: LiveKit connect once, no `Disconnected` handler (#5). Website: `user-join` once (#6). Backend: no restore after restart (B). Each client assumes the connection it made at page load is the one it still has. Phones, Wi-Fi hand-offs and pm2 restarts all violate that assumption daily. **PROVEN IN CODE**.

**E. Production edited in place.** `/root/djpanel_backend` was not a git repository until Oct 20 and matches no repo (`audio_stream_socket.io` is an old copy); the panel's `package-lock.json` had been hand-edited on the server and an untracked `server.js` sits in its tree; the Oct 14 metadata fix and the Oct 20 crash fixes were applied by patch script on the box. There is no way to say what ran at 18:19 on Oct 16 except by reading the file now. → every incident's investigation cost; #1's slow diagnosis. **PROVEN**.

**F. Unpinned dependencies and images.** `next: ^14.0.1` resolved to 16.3.5 on a rebuild and silently changed URL parsing (#4). `react: ^18` runs React 19. The LiveKit container's pin is unknown (no compose file in any repo). A rebuild is a release nobody reviewed. **PROVEN** for Next; **INFERRED** for LiveKit until `collect-evidence.sh` reports the image digest.

**G. TLS verification disabled.** `NODE_TLS_REJECT_UNAUTHORIZED=0` in the panel's `.env.local` (and in the developer machine's environment). Not a cause of any of the five, but it means the panel would happily talk to an impostor Mongo/SMTP/LiveKit endpoint, which matters on a compromised host. **PROVEN**.

**H. Unauthenticated token route granting publish rights.** `GET /api/v1/token?room=X&isAdmin=true` returns identity `admin` with `canPublish: true` to anyone, no cookie required; listeners also get `canPublish: true`. Anyone on the internet can take over the station's audio or kick the DJ, which is indistinguishable from #5 from the outside. **PROVEN** (route source; `canPublish: true` in the listener JWT fetched during this session). Not implicated in the five incidents (**INFERRED** negative: the LiveKit log should show no `admin` joins from IPs other than the DJs').

**I. Nothing was observing.** pm2 logs have no timestamps; nobody is subscribed to the stream; crashes at show start were in the error log since July and read for the first time on Oct 20. The client was the monitoring system, and two customers resigned from that job. → all five. **PROVEN** by the fact that every incident in the table was reported by the client first.

**J. Host hygiene.** EOL Ubuntu, 353-day uptime, root password SSH under brute force, unknown systemd user units, both boxes sharing one hostname. Not the cause of any of the five, but it decides what can be trusted and makes "clean git trees" meaningless until the box is rebuilt. **PROVEN** indicators; containment **not proven** (see `compromise-containment.md`).

**K. Schedule and time handling pushes DJs into the failure modes above.** UTC-fixed slot times, wall-clock feed shown as UTC, approval not unlocking Go Live, tones required to unlock: DJs who cannot go live when they expect to open more tabs, reload, re-press Go Live, which under A becomes #5. **PROVEN IN CODE** for the time handling; the behavioural link is **INFERRED**.
